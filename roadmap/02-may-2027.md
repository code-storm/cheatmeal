# May 2027 — H2 Phase 1: Foundations for the three H2 bets

**Theme:** before committing real feature work to light social, native evaluation, or content expansion, lay the specific technical prerequisites each one needs — and branch hard if H1's retention number came in bad.

## Retention-shortfall contingency (read this first)

If the end-of-April decision gate showed D7 retention near the ~8% industry baseline rather than H1's modeled 30–45%, **May's entire scope collapses**: re-run H1-Phase-1-style reminder/cadence tuning using now-real analytics data, and defer all three H2 focus areas by at least one month. This is the one case where Track A and Track B converge onto identical scope regardless of team size — growth work on top of an unvalidated retention base is wasted effort. Everything below assumes retention came in close enough to the model to proceed.

## Carried-forward risk check-in

Branded-event sourcing doesn't resurface this month (no new event is being negotiated yet — see [05-aug-2027.md](05-aug-2027.md)). Solo-founder bandwidth is the reason Track A's May scope is "scope, don't build" rather than "build" on three of four items.

## Track A — still solo/bootstrapped

- **Migrate Tokidoki's static event-tier content into the DB-backed `EventTier` model.** Today, `server/src/content/events.ts`'s `EventTierSeed` is read directly by `events.service.ts::resolveEventTiers` for the Tokidoki event, while the DB `EventTier` model (`prisma/schema.prisma`, referenced via `PregnancyProfile.tierGrants` and `Event.eventTiers`) is only populated for admin-*created* events. This means admins can't edit Tokidoki's own ladder through the admin portal today. Migrating resolves the inconsistency and is a prerequisite for content expansion's planned later branded/seasonal events being fully admin-manageable.
- **Scope (don't build) S3/R2 object storage** to replace `adminUpload.routes.ts`'s broken-in-prod local-disk upload (it writes to a path that only resolves when server and client are sibling checkouts in local dev — Render and Vercel share no filesystem). Pick the provider (R2 is the natural fit given the already-near-zero-cost stack — no egress fees); write the actual integration in June, not May.
- **Light-social foundation:** extend the Bump Squad backend aggregation (already reading `PregnancyProfile.lmpDate`) to surface each cohort's streak/points *trend* — week-over-week delta, not just a snapshot leaderboard. Still zero new UGC, zero new PII, same table, same no-chat/no-DM/no-profile constraint H1 Phase 3 set.
- **Native-eval instrumentation:** add session length, PWA "Add to Home Screen" conversion rate, and Android vs. other OS split on top of H1 Phase 1's analytics. Cheap (same homegrown table), and must exist before July's native-eval decision can be evidence-based rather than a guess.
- **Content-expansion foundation:** write (don't ship) a one-page content-model decision for postpartum/new-parent weeks — does `planGenerator.service.ts`'s existing week-indexed pattern extend past week 40 into "postpartum week N," or does it need a parallel model keyed off a delivery date? Settle this before June's content work starts.

## Track B — if team/funding grows

- Same Tokidoki/`EventTier` migration and same light-social trend work as Track A — cheap and correct regardless of team size, no reason to skip.
- **Actually build** the S3/R2 integration this month, not just scope it.
- **Begin admin RBAC/multi-admin work.** `requireAdminAuth.ts`/`adminAuth.service.ts` implement a single flat admin role with a 12-hour JWT today — no multi-admin, no team management. This is the first genuinely Track-B-only ticket in the whole roadmap: it's only needed once a second person touches the admin portal.
- Same native-eval instrumentation as Track A, plus a lightweight Capacitor/Expo packaging spike (not a full build) to test Play Store feasibility — cheap to attempt with more hands, and gives July's native decision a real prototype instead of a desk estimate.
